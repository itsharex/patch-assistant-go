## 修：点补丁树里的文件，连线不加粗（用户报的"点了没高亮"）

用户截图反馈：在补丁树（右侧）点一个文件，左侧连线没有加粗。

### 根因（不是连线层的问题，是选中态被冲掉了）

`makeRow` 给"补丁树里有对应项的**文件**行"挂了一个单击处理器（见 app.js 里
`if (treeKey === 'patch' && !node.dir && node.mapped)`），单击 200ms 后调
`locateCounterpart()` 去应用树定位对端。而 `locateCounterpart` 原来**无条件**
`apply(r.state)` —— 整体重渲染两棵树，`.row.selected` 跟着 DOM 一起没了。
于是：点 → 选中 → 连线加粗（约 200ms）→ 重渲染 → 选中消失 → 连线变回细的。
用户看到的就是"点了没高亮"。

排查手法：截图里左侧被"闪"到的那一行底色是 `#dbe8fd` + 蓝色 outline ——
那是 `.row.located`（flashRow，3 秒），不是 `.row.selected`。两棵树的选中底色
（`--row-sel`）扫一遍发现右边根本没有，说明不是 `linksFocus` 判错，而是
选中态本身已经不在了。

### 改法

1. **选中态跨重渲染保活**（app.js）：新增 `sel = {app, patch}` 记 dom 路径、
   `selRoot` 记上次渲染的根路径。
   - `setSelectedRow` 里记 `sel[row.__tree] = row.__dom`
   - `renderTree` 重建完按 dom 从 `links.index[treeKey]` 取回那一行补 `.selected`
   - 根路径变了（换了包）就作废，不接回去
   - `reMatch` / `pickAndOpen` 里显式清空 `sel`（重新匹配后结构可能变，
     接回去会指到别的文件 —— 这是原 `.row.located` 注释里就担心过的事）
2. **定位优先走快路径**：先 `revealRow` 试一次，能定位就不 `apply`。
   重渲染会丢滚动位置、丢展开的嵌套 jar、丢选中态，为了"跳过去看一眼"不值当。
   只有祖先链真变了（后端现场解压了嵌套 jar，前端没有那些子级）才 `apply`。
3. **对端也选中**：`flashRow(row)` 之后 `setSelectedRow(对端树, row)`。
   两端都亮 + 中间那条线加粗 = "我点的这个文件在对面哪儿"一句话说完。
   闪一下的 outline 保留，3 秒后只剩持久选中。

### 验证

`make_harness.py` 里把替身补成能跑真实路径：`LocateMapped` 按真实语义回
`{side, ancestors, path, state}`（祖先链按 dom 前缀逐层从 DOM 上取 `__node.path`），
再加 `?click=patch`（点补丁树第 2 行）和 `?rerender=1`（点完再强制 apply 一次）。

结果：`locErr=None`，`focus={app: 对端 dom, patch: 被点的 dom}`，
只有那一对 `focus=True`，且强制重渲染之后依然如此 —— 说明保活生效。
截图 `click-patch.png` 能看到那条加粗的蓝线。

### 顺带记下

- `.row.located`（flashRow）= `--row-sel` 底色 + `outline: 1px accent`，3 秒后消失。
  看到"蓝色但带 outline"的行是它，不是选中行。
- 无头 Chrome 里 `--dump-dom` 不会跑 rAF，探针必须直接同步调 `__draw()`；
  导出时机要排在"单击延迟 200ms + 定位"之后（现在 resize 在 +800ms、导出在 +900ms）。

## 加：「临时补丁」可以整体撤销（用户报"取消不掉"）

用户报：标记删除之后关掉软件重开，删除标记还在；想取消却取消不掉。

### 现状（为什么取消不掉）

- 标记删除**可以**在应用树上反向点一次（`MarkDeleteAppNode` 是切换项，
  右键「标记删除」带 ✓，再点取消），但前提是那个节点还在树上。
- **物理删除（「删除」菜单）根本没有反向操作**：`DeleteAppNode` 把节点从
  children 里摘掉了，右键都找不到它，而记录还在磁盘上
  （`%APPDATA%/.../manual_deletes/<sha1>.json`），下次打开照样重删一遍。
- `manualdel.Store.Clear()` 早就写好了（注释里就写着"用户主动点了恢复原状"），
  但**没有任何 UI 调它** —— 只有 RunPatch 成功写包后自动清。所以这个能力
  一直是死的。

### 改法

- Go：`App.ResetManualDel()` = 清记录 + `OpenAppPack(原路径)` 重新解析。
  顺序不能反：`OpenAppPack` 内部会 `reapplyManualDel`，记录还在就等于白重开。
  重解析顺带把 total 重算、refresh() 重跑匹配。
- `State.ManualDelPending`（磁盘上还有没有本包的删除记录）+ App 字段
  `manualDelPendingNow` 缓存：菜单是**逐节点**生成的，直接在 `appMenu` 里读
  文件就是几千次读，所以在 `state()` 开头算一次。
- 应用树右键新增「恢复原状（撤销删除）」：claim 是 `manualDelPendingNow`。
  这是物理删除唯一能撤销的入口。
- 「临时补丁」面板头新增「全部撤销」按钮（`.btn-sm`），和上面同一个动作。
- 两处都先 `confirm()`：要重读一遍 jar，大包几秒。
- 撤销前清 `sel`（dom 路径会整体前移，接回去会指错行）。

### 测试

`gui/app_test.go` 的 `TestResetManualDel`：标删→撤销→回到 none；
物理删除→撤销→节点回到树上且 total.ManualDel 归零；再关重开确认记录真的没了。

### 界面核对

harness 加 `?tmpdel=1`（往 state.json 里塞 3 条 manualDelList），
截图 `temp-patch-reset.png` 能看到面板头和「全部撤销」按钮。

## 改：点遮罩不再关弹窗（全界面统一）

用户报："点弹窗以外的地方也会取消掉这个弹窗，全部改掉"。

原来六个弹窗各挂了一个 `if (e.target === 遮罩) 关掉`：搜索、对比、确认、
设置、签名、绑定信息。全部删掉，出口只剩：

- 各自的「确定 / 取消」按钮

- Esc —— 全局 keydown 里统一收，**确认框排在最前面并 return**
  （否则 Esc 会把底下的设置框一起关掉，而确认框的 Promise 永远挂着）

理由写进了 `init()` 的注释里，只留这一处说明，其它五处只留一句指向它的
注释 —— 六个地方各写一遍同样的道理，以后改的时候容易改漏。

无头 Chrome 验证：harness 的 `?confirm=1` 先点「全部撤销」弹出确认框，
**再对遮罩 `click()` 一次**，导出 `confirmOpen` → `True`，说明点外面不关了。

构建产物核对（`gui/build/bin/PatchAssistant2J.exe`）：
`_harness` / `_app_dbg` / `window.__` 均 absent，
`resetManualDel` / `confirm-overlay` / 注释原文 FOUND。

## 加：拖单个文件到具体文件行 = 替换内容 + 「单包视图」

用户报：拖单个文件（.class/.java 或 .jar）进去，左侧弹「应用包只接受 1 个 .jar 文件」，
想要的是"把文件拖到具体应用文件上替换内容"，并提议加一个只显示 jar 这侧的视图。

### 落点表现（用户确认）
松手后弹「应用包只接受 1 个 .jar 文件」—— 说明 Wails 拖放管线本身是通的
（坐标能被 Go 解析），不是高 DPI 下 Atoi 静默失败那类 bug；所以只按"类型规则拦掉"处理。

### 改法（前端 + 后端一起分流）
- Go 新增 `HandleDrop(side, rowPath, paths)` 总入口：
  - 落在**具体文件行**（rowPath 非空）且拖的是**普通文件**（非 .jar/.zip、非目录）
    → `ReplaceNodeContent`：用磁盘文件换掉该节点内容（SetFileSource + 清 Md5/Size 缓存 + SetEdited(true)）。
  - 落在**空白处**又拖了普通文件 → 友好提示「这类文件要拖到左侧具体应用文件上才能替换内容；拖整包请使用 .jar / .zip 或目录」。
  - 其余（空白 + 整包；或落在行上但拖的是整包）→ 原 `HandleFileDrop` 打开包语义。
- `ReplaceNodeContent` 复用编辑内容的同一条机制（ConsumeBytes → writer），
  所以"替换"和"编辑内容"一样只改内存、重新加载会丢弃。目录节点 / 拖入目录都拒绝。
- 前端 `initDrop` 抽出 `onFileDrop(x,y,paths)`：`document.elementFromPoint` 取 `.row`，
  看是不是文件行（目录行不算），连同 rowPath 送 Go；替换成功 toast 区分「已替换」/「已打开」。
- 新增「单包视图」按钮（工具栏）：切 `body.single-app`，CSS 隐藏补丁面板 / 分隔条 /
  补丁信息栏，app 面板占满，方便拖文件替换。再点还原（`linksSchedule` 重排连线）。
- CSS：`.row.wails-drop-target-active:not(.expandable)` 给"要替换的那一行"加高亮，
  让用户看清落点（Wails 会把 class 加到带 `--wails-drop-target` 的祖先，含 .row）。

### 测试
- `TestReplaceNodeContent`：替换后节点 edited=true、ContentBytes=新内容、
  打补丁产物里是该内容、重新加载丢弃替换。
- `TestHandleDropRoutesToFileRow`：文件行+普通文件→替换；空白+普通文件→友好报错；
  文件行+.jar→走打开包不报错。

### 核对
`node --check` / `go vet` / `go test ./...` 全绿；`wails build -tags webview2` 成功，
exe 含 `ReplaceNodeContent` / `HandleDrop` / `single-app` / `单包视图`，无 `_harness`/`window.__` 残留。

### 顺带提示（未改）
Wails 原生 `postMessageWithAdditionalObjects('file:drop:'+e.x+':'+e.y,...)`
发的是**小数坐标**，Go 侧 `strconv.Atoi` 在 125%/150% 缩放下会失败、整次拖放被静默丢掉。

## 补：树里没有的文件也能拖进来（新增，不是替换）

用户追问："我想拉进去的左侧目录树没有的话，不就不能替换嘛"。
上一版只能**替换已存在的节点**，新文件无路可走。补一条"新增"：

### 拖放现在三路分流（`HandleDrop(side, rowPath, rowIsDir, paths)`）
1. 普通文件 + **文件行** → `ReplaceNodeContent`（替换）。
2. 普通文件 + **目录行 / 空白处** → `addOrReplaceChild`（新增）：
   - 目录行：加进该目录；空白处：加到根；
   - 目录里已有同名子节点 → 替换它，**不会**加出两个同路径条目
     （zip 同路径重复会让解压结果不确定）。
3. 整包（.jar/.zip/目录）→ `HandleFileDrop`（打开包），与落点无关。

### 新增节点怎么造
`tree.NewFile(name, childPath, fi.Size(), now, nil, isPatch)` +
`Kind = tree.KindFileDirect`（语义正是"用户直接拖进来的文件"）+ `SetFileSource(src)` +
`SetEdited(true)` + `Parent` + append 到 `parent.Children`。
写包遍历的是整棵树，所以新节点自动进产物 —— 不需要改 writer。
**注意**：目录节点的 `Path` 带尾斜杠（与 zip 条目一致），所以
`JoinPath("a/b/", "X.class")` 才对；根节点是合成容器，`Dir()` 未必为真，
不能拿它做"不是目录"的拒绝（踩过：`目标不是目录: `）。

### 补丁侧禁止新增
补丁树节点要靠"匹配"才能落到产物上，直接塞新节点没有对应应用侧节点、
写包时会被忽略。所以 `side != app` 的新增直接拒绝并说明原因，
不骗用户"加上了"。

### 高亮改成只亮最深那一行
Wails 的 `wails-drop-target-active` 会加到落点**及所有祖先**，深层文件会让整列
目录一起亮，看不出落点。改为 `trackDropRow()`：dragover 时
`elementFromPoint` 取最近 `.row`，只给它挂 `.drop-row`（dragover 同步、drop/dragend
/拖出窗口清掉）。文件行亮=替换、目录行亮=加进这个目录。

### 测试
`TestHandleDropAddsNewFile`：目录行新增 → 树里有 + edited + 产物里有；
空白处新增到根；同名再拖一次 → 只 1 个同路径条目且产物是第二次的内容；
补丁侧新增被拒绝。`TestHandleDropRoutesToFileRow` 改成四参签名。

全量 `go test ./...` / `node --check` / `go vet` 全绿，`wails build` 成功。

## 加：忘了路径也能打补丁 —— 拖到补丁侧按文件名反查

用户："我忘了路径了，但我有文件。拖到右边后它搜索出匹配的文件……你觉得呢"。
（他提的"加载临时目录"没做：直接把文件绑到命中节点上即可，少一次
"拷到临时目录再当补丁包读回来"的往返，结果完全一样。）

### 交互
- 普通文件拖到**补丁侧**（目录行或空白处）→ `FindAppCandidates(name)` 在应用树里
  按文件名（`EqualFold`，大小写不敏感）反查：
  - 命中 1 个 → 直接 `ReplaceNodeContent`，并**滚到该文件、闪一下**
    （`LocateNode` 拿祖先链 + `revealRow`/`flashRow`）；
  - 命中多个 → 回 `matchMany` + 候选，前端弹 `#match-overlay` 让用户挑一个；
  - 命中 0 个 → 回 `matchNone`，提示"应用包里没有同名文件"。
- 落在**文件行**仍是替换、落在**应用侧**目录/空白仍是新增（见上一节）。

### HandleDrop 返回值改成 DropResult
以前直接回 `*State`，但"要用户先挑一个"的时候还没有新状态可回。
现在 `{action, state?, path?, candidates?, fileName?, srcPath?}`：
`open / replace / add / matchMany / matchNone`。前端按 action 分支。

### 只搜已加载的树（刻意）
嵌套 jar 里的条目是惰性展开的，没展开就搜不到。为了搜个名字把每个嵌套 jar
都解开，大包要几十秒，不值。要搜里面的就先展开那个 jar。

- 发现 `LocateNode` 早就有了（临时补丁清单用它定位标删节点），直接复用，
  不用新写（我先写了一个重名版本，vet 报 duplicate 才发现）。
- `#match-overlay` 走和其它弹窗同一套规矩：点遮罩不关，出口是选一行 / 取消 / Esc；
  Esc 在全局 keydown 里排在 confirm 之后 `return`，避免 Promise 悬着。

### 测试
`TestDropLooseFileMatchesByName`：单命中→replace+路径对+内容进产物+`LocateNode`
能拿到祖先；无命中→matchNone；另造一个两处 `Dup.class` 的 jar→matchMany+2 候选+SrcPath。
`TestHandleDropAddsNewFile` 末尾那段"补丁侧拒绝新增"改成"按名反查命中已加的
root-added.txt → replace"。

## 修：按名反查搜不到嵌套 jar 里的类（用户截图报的）

用户拖 `CallMethodInvokerAbstract.class` 到右侧，提示"应用包里没有同名文件"，
但文件明明在包里。原因：它藏在 `BOOT-INF/lib/*.jar` 里，那些 jar 默认折叠，
第一版只搜**已加载的树**，所以搜不到。Spring Boot 胖包的业务类大多就在那里，
这个限制等于把功能废掉一半。

### 改法
- `FindAppCandidates` 现在会**只读地**进嵌套 jar 里搜：
  - jar 已展开（`Children != nil`）→ 直接走子级；
  - 没展开 → `readZipTree(n)` 把 jar 解成一棵**临时树**、扫一遍条目名，用完即弃。
- **不挂到原树上**是关键：一旦给 jar 节点建了子级，`writeTreeNode2PackWithJar`
  就认为"内部改过"而重打包它（临时文件 + STORED + 当前时间）。为了搜个名字
  把所有 jar 都重打一遍，代价太大、还会改动无关字节。
- 真正替换时才展开**命中的那一个**：`resolveNode` 里 `BuildChildrenWithCompress`。
- 嵌套条目用**定位串** `BOOT-INF/lib/x.jar!/com/foo/Bar.class` 标识 ——
  嵌套条目的 `Node.Path` 是相对的、全树会重名，必须带 jar 前缀才唯一。
  `joinLoc` / `splitLoc` / `resolveNode` 负责拼与解；
  `ReplaceNodeContent` 和 `LocateNode` 都改走 `resolveNode`，所以替换与"滚到眼前"
  对嵌套条目同样成立。
- 坑：从 `RootNode()` 开始走会把根（Name 是磁盘 jar 路径）当嵌套 jar，
  给所有命中套上 `xxx.jar!/` 前缀。改成从 `root.Children` 开始走。

### 测试
`TestDropLooseFileMatchesInsideNestedJar`（用 `nestedJarFixture`）：
命中 `BOOT-INF/lib/libA-1.0.0.jar!/com/example/Target.class` → replace；
产物里**嵌套 zip 内**的条目是新内容；
**未命中的 libB 字节必须与原包完全一致**（钉住"搜索不展开无关 jar"这条边界）。

## 改：单命中不再自动替换，一律先让用户挑（用户反馈"太生硬"）

用户原话："现在显示这样的太生硬了，我希望我把文件拖动到右侧之后，路径匹配之后我在选择"。
上一版只有**多命中**才弹候选，单命中直接替换 + toast，用户看不到"替换到哪去了"，
一旦反查错（同名但不同位置的类）没法拦。

### 改法
- `matchLooseIntoApp`：`len(cands) >= 1` 一律返回 `matchMany`，**不自动替换**。
  `matchNone` 只留 0 命中。前端拿到候选后必须用户点一行才 `ReplaceNodeContent`。
- 弹窗按命中数分两种形态：
  - `n == 1` → 标题「确认替换」，提示「在应用包里找到同名文件「X」，确认替换它？」，
    显示主按钮「替换」；
  - `n > 1` → 标题「选择要替换的文件」，页脚提示「单击一行即替换」，不显示主按钮
    （点了就是选了，再要个确认按钮反而多一步）。
- 候选项渲染成**两行**：`.match-path` 是包内条目路径（`word-break: break-all` 换行，
  **不省略**），`.match-jar` 是「在 xxx.jar」小字。原来单行 + 省略号，
  嵌套 jar 里几个同名类长得一模一样、分不出是谁 —— jar 名正是唯一的区分点，不能截。
- 键盘 ↑/↓ 移动、Enter 确认，Esc 取消（在全局 keydown 里排在 confirm 之后）。

### 测试
`TestDropLooseFileMatchesByName` 的"单命中"断言从 replace 改成
**matchMany + 恰好 1 个候选 + SrcPath**，再显式调 `ReplaceNodeContent` 验证内容进产物。

## 改：同名候选从弹窗搬进「补丁信息」面板，点行定位、看过再替换

用户："能否把匹配到的路径文件放在下方补丁信息里面，然后我点击后跳转，
查看没问题才进行替换，这样是不是更保险一点"。

上一版是弹窗里点一行**直接替换**。问题在于弹窗正好挡住树，而这一步的关键
恰恰是看树（路径对不对、旁边是不是那个类）—— 等于"没看就动手"。

### 交互
拖单文件到右侧 → 命中结果落到「补丁信息」面板顶部的清单里（不再弹窗）：
1. 点清单一行 → `pendingSelect` → `revealByPath('app', …)` 在应用树里展开/滚动/
   高亮/选中，**不动内容**；
2. 看过没问题 → 点右上角「替换到选中项」→ 才 `ReplaceNodeContent`。
   「替换到选中项」在没选中时 disabled —— 物理上不给你盲点。

### 实现要点
- 状态一份 `pending = { srcPath, fileName, candidates, sel }`；新拖入顶掉旧的。
- 清单块是 `.info-pane` 里 `<pre class="info-body">` 的**兄弟**，不在 pre 内 ——
  `apply()` 每次都重写 `#info-body` 的 textContent，塞在 pre 里会被冲掉。
- 单包视图（`body.single-app`）原本连 `.info-pane` 一起藏。这是"拖单文件替换"
  的主场，清单住在那个面板里，一起藏掉等于拖完什么都看不见 →
  `body.single-app.has-pending .info-pane { display: flex }`。
- 面板默认 150px 放不下三条候选 → `body.pending-tall .info-pane { min-height: 300px }`。
  只在**真的有候选**时抬（`pending-tall`），"没匹配到"只占一行，别浪费树的地方。
- `.pending { flex: 0 1 auto; max-height: calc(100% - 80px) }`：候选多时清单自己滚，
  给下面「补丁信息」正文留两行（那里可能是"两边同一个文件"这类警告）。
- `revealByPath` 改成返回 `Promise<boolean>`。其它调用方照旧忽略返回值；
  `pendingSelect` 要看 —— **定位失败就等于用户没看见**，得弹提示，
  不能让他以为看过了还照点替换。
- `apply()` 里换应用包时顺手 `clearPending()`：新包里旧路径没有意义。
- Esc 不管这个清单（它不是弹窗、没挡东西），出口是「取消」按钮 ——
  否则在设置框里按 Esc 会把刚拖进来的匹配结果一起清掉。
- 后端 `DropResult` 加 `SrcSize`：头部显示「拖入 147 KB · …」，
  和候选那一列的大小并排，是判断"版本对不对"最快的线索（比看文件名可靠）。

### 测试
`TestDropLooseFileMatchesByName` 增加 `SrcSize` 断言（len("MATCHED-BY-NAME")）。

## 修：按名反查的假否定（"树上明明有，拖进去说没有"）

用户拖 `CallMethodInvokerAbstract.class` 到右侧，提示没有；而应用树上那一行
明明就在（`pay-common-business/.../invoker/` 下，还连着补丁侧的映射线）。

### 根因
`FindAppCandidates` **只走内存树**。而内存树只反映"打开那一刻 + 用户展开过的
部分"：没展开的目录、被裁剪过的子树都不在里面。拿它当全集去回答
"包里有没有这个文件" —— 这是这条功能**唯一的输出** —— 就会给出假否定。
更糟的是失败信息只有一句"没有同名文件"，用户没法判断是真没有还是没查到。

排查过程记一笔：先按用户截图里的 jar 名去读磁盘上那个文件，发现它只有 292 个
条目、根本没有 pay-common（说明截图里的包不是现在这个文件，或被替换过）。
所以**不能靠复现用户那个包**，得从"搜索依赖了什么"上找问题。

### 改法（两遍式）
1. 第一遍走内存树：**用户改过的内容只在这里**（拖进来的新文件磁盘上没有），
   所以必须查；不碰磁盘，很快。未展开的嵌套 jar 跳过，交给第二遍。
   返回"这棵子树是否已完整覆盖"，只有**递归完整**的 jar 才记进 `covered` ——
   一个展开过的 jar 里若夹着没展开的嵌套 jar，就不算覆盖完。
2. 第二遍直接扫磁盘原包：`pack.BuildZipTree`（**只读中央目录，不解压**，
   几百 MB 的包也是毫秒级），走所有层级的条目名；嵌套 jar 逐个读进来再扫，
   `covered` 里的跳过。jar 套 jar 递归到 3 层。
3. **两遍都跑，不提前返回**：少一个候选和"一个都没有"一样糟 —— 清单少一项，
   用户就会以为只有那一处。

### 配套
- `resolveNode` 拆出递归的 `resolveIn`：搜索侧能钻到
  `a.jar!/lib/b.jar!/com/foo/Bar.class`，替换侧就必须能解析同样的串，
  否则是"清单里点得到、一点替换就报找不到节点"的半截功能。
- `DropResult.ScanNote`：没命中时前端显示「已检查 N 个文件、M 个嵌套 jar」。
  真实包上实测 110716 个文件 / 382 个 jar，耗时 ~375ms（命中时 ~160ms）。
- 前端口径：`已检查…，没有同名文件 —— 可以直接把文件拖到某个文件行上替换，
  或拖到目录行上新增`。

### 测试
- `TestFindAppCandidatesSurvivesTrimmedTree`：把中间目录 `Children` 清空，
  搜索仍必须命中（第一遍看不见，靠第二遍）。
- `TestFindAppCandidatesJarInJar`：三层包 `app.jar!/mid.jar!/inner.jar!/x.class`，
  候选定位串对、`LocateNode` 带祖先链、替换后最内层条目变成新内容。
- `TestFindAppCandidatesScanNoteOnMiss`：没命中时 `ScanNote` 必须说明查了多少。

## 真相：那个"树上明明有"的节点根本不是包里的文件（MappedNode 占位）

上一轮修的两遍式搜索是对的，但用户还是提示没有。这次用**真实包**查清了：

`20261015_GS_PAY320_测试工具.zip` 的 README 写着
`CallMethodInvokerAbstract.class → BOOT-INF/lib/pay-common-business/gfmis/bgtex/stamp/handler/invoker/CallMethodInvokerAbstract.class`，
而应用包里**没有这个路径**（`grep pay-common-business` 在整个 jar 里 0 次，
196 个嵌套 jar 逐个解开也没有）。指令是 ADD，于是匹配阶段
（`service.doMatchMappedNodeChildrenWithReadme`）沿路径造了一串 VirtualNode
目录 + 一个 MappedNode 文件。

**MappedNode 在树上和真文件长得一模一样**：有名字、有大小、有时间、还连着映射线。
用户照着树去找，当然觉得"明明有"。而它只是"补丁要新增的位置"。

探针实测（真实包）：
```
action=matchNone 候选=0 占位=1
  占位: BOOT-INF/lib/pay-common-business/.../CallMethodInvokerAbstract.class (17556 字节)
note="已检查 51802 个文件、220 个嵌套 jar（1 个压缩包打不开，已跳过）"
```
note 和用户截图里那行完全一致 —— 诊断闭环。

### 改法
- `findAppCandidates` 的**内存树那一遍要排除 `KindMapped`**。不排除的话它会被
  当成真候选列出来，用户一替换就凭空给包里多出一个从来没有的文件（不是替换，
  是新增），比"找不到"更坑。
- 新增 `findMappedPlaceholders`：真候选为 0 时，把同名的 MappedNode 单独收出来，
  放进 `DropResult.Placeholders`，前端用「补丁新增」标签 + 灰字列出来（点它只定位、
  不能选中替换）。
- 提示改成三种口径（用户的下一步动作完全不同）：
  1. 有候选 → 点一行定位，确认无误再替换；
  2. 只有占位 → "这些位置是补丁按 README 新建的，包里原本没有这个文件 ——
     要换成你这份，请把文件拖到补丁树里同名的那一行"；
  3. 真没有 → "已检查 N 个文件、M 个嵌套 jar，没有同名文件……"。
- `note` 里"jar 打不开"改成"压缩包打不开"：实测踩到一个叫
  `static/templates/framework/frame/download/year-compare-template.zip` 的普通
  资源文件，按扩展名被当压缩包试开然后失败。说成"jar 打不开"会吓人。

### 测试
`TestFindAppCandidatesReportsMappedPlaceholders`：造一个 README 映射到
`BOOT-INF/classes/new/deep/Brand.class`（包里没有）的补丁 → 树上出现占位节点、
`FindAppCandidates` 返回 0 候选、`HandleDrop` 回 matchNone 且 Placeholders 恰好一条。

## 拖入反馈：右侧显示文件名 + 按路径匹配

用户提的两件事：「拖进去文件的时候右侧也显示文件名」「再出现这种没有的文件时，
支持单独粘贴路径，然后按照路径来匹配」。

### 1. 右侧「拖入的文件」条（`#drop-file`）
- 位置：`#pane-patch` 内、`#temp-patch` 之上（`.pane` 是 flex column，`flex: none`）。
- 显示：文件名 + 体积 + 完整磁盘路径；多文件显示"xxx 等 N 个"；`清除` 只抹记录。
- **只记不改**：真正动作仍由 `HandleDrop` 决定（替换 / 新增 / 按名反查）。
  所以条上没有"确认"类按钮，避免让人以为这一步会动包内容。
- 何时显示：`side === 'patch'` 且不是单包（`.jar/.zip/.war/.ear`）拖入；
  `action === 'open'` 时清掉（头部 `#patch-path` 已经显示包路径，重复）。
- 体积要等后端 `stat`：`DropResult.SrcSize` 现在 replace / add / matchNone 都带上
  （新增 `fileSize()` 小工具，取不到返回 0，不影响主流程）。

### 2. 按路径匹配（`ResolveAppPath` + `normalizeInsidePath`）
- 入口在 `#pending` 底部（`#pending-path-input` + `定位`，回车等同点击）。
  只在"没匹配到"时出现 —— 正好是用户需要它的那一刻。
- 清洗放 Go 侧（前端只传原文），避免两套规则各修各的：
  去空白/引号、`\`→`/`、去前导 `/`、带上级目录时按 `BOOT-INF/` `WEB-INF/` `META-INF/`
  锚点切（取最靠前那个）；**不做模糊猜测** —— 猜错会替换到别的文件上。
- 三种结果分开表达（下一步动作不同）：
  正常 → 高亮 + 定位，可替换；`Placeholder`（MappedNode）→ 只定位 + 提示
  "是补丁新增的位置"，**不替换**（替换等于凭空往应用包里加文件）；
  `Missing` → 回显清洗后的路径 + 提示不存在，**不报错**（手输错字是常态）。
- `matchNone` 也必须回 `SrcPath`，否则"按路径定位 → 替换"这条路断在最后一步。

### 踩到的坑
- `.pending { display: flex }` 压过 UA 的 `[hidden]{display:none}` → 没有待替换时
  面板顶部一直挂着空标题行 + 输入框。补 `.pending[hidden]{display:none}`。
  本项目已有 15 处同类规则，**凡是自己设了 display 的块都必须补**。
- `pending-tall` 的 min-height 300 → **340**：多了按路径那一行后，3 条候选的最后
  一条被切掉一半，用户会以为"就这些了"。
- 用 bash heredoc 追加 Go 测试时 `\n` `\t` 被吃成 `/n` `/t`（README 夹具因此
  解析不出来，占位节点根本没生成，白查半天）。**追加含转义的代码一律用编辑工具**。

### 测试
`TestNormalizeInsidePath`（16 组：引号/反斜杠/盘符/WEB-INF/META-INF/多锚点/`!/`/空）、
`TestResolveAppPath`（四种粘贴方式同一目标 + 嵌套 `!/` + 不存在回 Missing + 空路径报错）、
`TestResolveAppPathMappedPlaceholder`（占位节点标 Placeholder 而非 Missing）、
`TestDropLooseFileMissKeepsSrcPath`（matchNone 带 SrcPath/SrcSize，且走完
定位→替换→`RunPatch` 产物是新内容）。

## 拖入两个文件只认一个 + 拖入后不展开

用户反馈："我拖入两个不知路径的文件时，提示这样的，并没有展开"。

### 根因一：`HandleDrop` 只用 `paths[0]`
一次拖 N 个文件，后端只拿第一个去反查，其余**无声丢弃**。用户拖了
`IPayIncomeService.class` + `CallMethodInvokerAbstract.class`，界面只显示前者的
1 处匹配。拿真实包（143 MB，桌面上的 pay-voucher-server-3.2.0）验证：后者其实
在 `BOOT-INF/lib/pay-common-business-3.2.0-SNAPSHOT.jar!/gfmis/bgtex/stamp/handler/invoker/`
里命中 1 处 —— 恰恰是用户最想看的那条。

修法：
- `DropResult` 去掉摊平的 `Candidates/Placeholders/ScanNote`，改成
  `Items []DropMatch`（每个拖入文件一条，自带 fileName/srcPath/srcSize）。
- `matchLooseIntoApp(src)` → `matchLooseFilesIntoApp(paths)`。
- **一次扫描回答多个名字**：`findAppCandidatesFor(names)`。第二遍要读几百 MB 的包
  （单次 ~0.4s），拖 5 个文件循环扫 5 遍纯属浪费；扫一遍时比对 5 个名字代价几乎一样。
  `FindAppCandidates(name)` 保持单名 API，内部走它。
- 前端 `pending` 从 `{srcPath, candidates, sel:path}` 改成
  `{items:[...], sel:{path, srcPath, fileName}}` —— 选中态必须记住"这行属于哪个文件"，
  否则多文件时会把 A 的内容写进 B 的位置。
- 多文件时清单按文件分组（`.pending-group` 细标题：文件名 + 命中数 + 体积），
  命中为 0 的组也要画出来（"这个没找到"本身就是用户最需要的信息）。

### 根因二："并没有展开" —— 只有一处命中时没自动定位
`showPending` 之前只渲染、不定位，要用户自己点那一行。只有 1 处候选时这步纯属多余，
而且"拖完树上什么都没发生"看起来就像没成功。现在：单文件 + 恰好 1 处候选 →
`pendingSelect` 自动展开/高亮/滚到视野（按钮随之可用，但替换仍需再点一次）。
真包验证 `LocateNode` 返回 6 层祖先（`BOOT-INF/` 起，目录条目带尾斜杠），
说明前端逐层 toggle 能走到位；补了 `TestLocateNodeFreshPackDeepPath` 钉住这点
（合成夹具的目录没有尾斜杠，两种形态都要能对上 NodeView.path）。

### 顺带
- 拖到**文件行**上只在拖 1 个文件时算替换；拖多个时退回按名反查（一个节点装不下多份）。
- 应用侧拖多个 → 逐个 `addOrReplaceChild`，`DropResult.Count` 记数量，提示"已加入 N 个文件"。
- 按路径定位（`ResolveAppPath`）在多文件场景下用 `pendingTargetItem()` 决定用哪份内容：
  已选中那行所属文件 → 只有一个文件 → 唯一没匹配到的那个 → 否则提示先点一行。

## 「复制路径」→ 粘贴 → 报"没有这个路径"：目录尾斜杠不一致（真 bug）

**现象**：右键树上 `factory` 目录 →「复制路径」得到
`BOOT-INF/lib/pay-common-business-3.2.0-SNAPSHOT.jar!/gfmis/.../invoker/factory`
（不带尾斜杠），粘进「按路径定位」→ "应用包里没有这个路径"。
可上一秒他还在树上点着它。

**根因**：同一个目录有两种写法。
- 树里目录的 `Path` **带**尾斜杠（`pack.buildFromZipReader` 的保真点：
  保留 zip 条目名原样，`META-INF/` 判签名就靠这个斜杠）；
- 没目录条目时补建的占位目录 `Path` **不带**（`getOrCreateParentNode`）；
- 而「复制路径」拼的是节点**名字**（`nodeDisplayPath`），目录名天然不带斜杠。

`resolveIn` 的叶子查找是 `findTreeNodeByPath`（精确比较），于是"复制出来再
粘回去"必然查不到 —— 用户看到的是"包里没有"。

**修法**：新增 `findTreeNodeByPathLoose`，精确没命中时再试 `path+"/"` 和
`trimSuffix("/")`，**只给 `resolveIn` 用**；其他地方保持精确匹配，
免得"差一个斜杠也算命中"把别的判断悄悄放宽。两个方向都容错。

## 粘进来的是目录 → 单独一种结果（`PathTarget.Dir`）

目录不能当替换目标（`ReplaceNodeContent` 本来就会挡，但那时候用户已经
"选中"了，等于让他白点一次）。所以：

- `ResolveAppPath` 命中目录时回 `Dir: true`，不回 `Size`（目录是 -1，
  显示成"未知大小"反而像出错）；
- 前端 `pendingPathDir`：先按最可能的意思试一次 **目录 + 手上这个文件名**
  （拖进来 expdp.txt、粘了 factory 的路径，多半就是"这个文件在 factory 里"）。
  拼出真文件就选中它，并在提示里明说是拼出来的，不装作原样命中；
- 拼不出来 → 定位目录 + 在输入框下方写解释（`#pending-note`）：
  "要替换文件，路径请粘到文件那一层；要把 X 新增到这个目录，
  把文件拖到应用树里刚定位的那一行"。

解释行为什么不用 toast：几秒就没了，而这是要照着做的下一步。

**踩到的坑**：解释行在输入框下面，默认 150px 的面板直接把它切掉 ——
截图里只看到输入框，"为什么不能替换"一个字都没露。加 `body.has-pathnote`
把面板抬到 340px（和 `pending-tall` 同一个数值）。

## 连带修掉：拖到**嵌套 jar 里的目录行**新增是断的

## 修：右側「拖入的文件」条不能直接往左侧应用树拖（用户报障）

用户截图 + 原话："现在好像不能直接吧这种文件从右边拖动到左侧里面"。他看到
右上角"拖入的文件"里列着 expdp.txt，想直接拖那一行进左边的 mapper 目录 —— 拖不动。

### 根因
整条拖放管线只走 **Wails 原生**通道（`window.runtime.OnFileDrop`），只有"真·从
资源管理器/桌面拖文件进窗口"才触发（app.js 约 1400 行注释解释了原因：浏览器出于
安全只给 File 对象、**不给真实路径**，而建树必须要路径）。而"拖入的文件"条是
**回执**：`<li>` 上既没有 `draggable`、也没有 dragstart 监听，所以那一行根本发起
不了拖拽 —— 用户没看错，是真的不能拖。

### 修法：让这条回执成为**窗口内**拖拽源
它本来就攥着磁盘路径，直接拿来做窗口内 HTML5 拖放，落点判定复用 `onFileDrop`
（替换/新增规则只有一份）。**后端零改动** —— `HandleDrop` 早就支持"拖到目录行
= 加进该目录"。

- 模块标志 `dragFromListPath`（正被从回执往树上拖的源路径，null=没在拖）。
  用它而不用 dataTransfer：dragover 阶段读不到 `getData`，而"拖动中高亮目标行"
  恰恰要在 dragover 就知道拖的是什么。
- `renderDropFile` 每行：`li.draggable = true` + dragstart 里置
  `dragFromListPath = f.path`、`effectAllowed='copy'`、setData 兜底。
- `initListDrag()`（在 `initDrop()` 里调一次）注册 window 的
  dragover/drop/dragend：仅当 `dragFromListPath` 有值才动手 →
  drop 里 `preventDefault()` + `onFileDrop(e.clientX, e.clientY, [p])`。
- `isFileDrag` 补 `if (dragFromListPath) return true;` —— 否则目标行不亮，
  松手前看不到会落在哪。
- CSS：`.dropfile-item { cursor: grab }` + `:active { cursor: grabbing }`。
- title 改成"路径 + 可拖到左侧应用树：目录行=新增，文件行=替换"。

全程只在 `dragFromListPath` 有值时动手 → 对原生 OS 拖放**零影响**（那时是 null）。
