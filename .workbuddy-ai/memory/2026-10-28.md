# 2026-10-28

## zip 条目名 GBK 乱码（`服务配置说明.docx` 显示成 `?`）

用户报障：「打开这种时，文件名会出现乱码」，截图里补丁包 `补丁包` 树下第三条是
`?????????.docx`。

### 先看真实字节，别猜

直接拿那个补丁包读中央目录：

```
flag=0x0000 | 服务配置说明.docx | b7fecef1c5e4d6c3cbb5c3f72e646f6378
```

`flag=0x0000` = 没有 UTF-8 标志位（0x800），名字是 GBK 字节。Go 的
`archive/zip` 在这种情况下**原样返回字节**（只把 `FileHeader.NonUTF8` 置真），
这些字节不是合法 UTF-8，经 JSON 到前端就成了 `�`。

`internal/pack/zip.go` 的包注释里其实早就写着这个 TODO（"需要在这里补 GBK 解码"），
一直没做。原版 Java 用 `new ZipInputStream(in, GBK)` 无条件按 GBK 解，所以那边没这问题。

### 改法：显示用解码名，写回用原始字节

不能只在建树时解码 —— `Path` 同时是**重打包时的条目名**
（`newEntryHeader` 直接 `Name: node.Path`），解了码就会把包里的名字从 GBK
悄悄改成 UTF-8，下游仍按 GBK 解名的工具（含原版 Java）立刻看到乱码。

所以拆成两份：

- `Node.Path` / `Name`：`util.DecodeZipEntryName` 解出的 UTF-8，给界面显示与匹配用；
- `Node.RawPath`：原始字节，只在"解码前后不同"时非空，写回时用它，
  并设 `zip.FileHeader.NonUTF8 = true`。

`NonUTF8` 那一步是必须的：不设的话 `archive/zip` 的 `writeHeader` 会按
"合法 UTF-8 且需要多字节"去加 0x800 标志，读回来就被当 UTF-8 解 ——
等于把 GBK 字节冒充成 UTF-8，比乱码更难查。

落点：
- `util.DecodeZipEntryName`：合法 UTF-8 原样返回 → 否则 GB18030 → 再失败才替换；
- `pack.buildFromZipReader` 解码 + `rawPathIfDecoded`，占位目录也从父节点的
  `RawPath` 取（`util.GetDirPath`）；
- `service.entryNameOf`（`writer.go`）给两处写入口共用：`newEntryHeader` 与
  `patchsave.go` 的 `writePatchPackWithZip`（它原本是独立构造 header 的）；
- `service.inheritRawPath`（`patch.go`）：补丁条目映射成应用侧节点时继承原始字节，
  否则"打补丁"会把补丁里新增的中文名文件写成 UTF-8。两个调用点的父节点都是目录，
  所以没复刻 `GetNodePathByParent` 里"父节点非目录就上溯祖父"那条分支；
- `jarcompare.go` 全部改用 `zipEntryName` —— 不只是显示，`entryFromZip` /
  `classInnerFiles` 拿树上的 `Path` 去和条目名比，不解码就永远不相等，
  预览会一直显示"这条不存在"。

### 测试

`DecodeZipEntryName`（GBK / UTF-8 两条）、建树三条（文件 / 目录 / ASCII 留空）、
写入三条（GBK 真写一遍再读回验字节与 0x800、新节点写 UTF-8、目录补尾斜杠）。
真实包实测：`服务配置说明.docx` 正常，`raw=b7fecef1…` 保留；101 MB 应用包 323 节点
零非法 UTF-8。

### 教训

- **"乱码"先看字节，别在解码层瞎猜**。一条 `flag=0x0000` 就定性了。
- **路径字段往往一身兼两职**（显示键 + 写回名）。要改其中一职，就得把另一职的
  原值单独存下来，否则修好显示、弄坏包。
- **`archive/zip` 缺标志位时不做任何猜测**。它把 `NonUTF8` 交给你，就等于把
  这个决定交给你 —— 读的时候要解，写的时候要明确告诉它"这名字不是 UTF-8"。

## 拖到行上的"同名"到底怎么算（用户追问：原先就有是覆盖吗）

用户问："我直接把一个 lib 包下的文件拖入到包中，如果这个包原先就有，那么是
覆盖还是怎么样"。

答案本来是"覆盖"，但顺着查发现两处与原版不一致：

### 1. 落在**文件行**上不是"就地替换这一行"

原版 `TreeNodeMatchProcessor.exec` 一律先算目标目录
（`appNode.isDir() ? appNode : appNode.getParent()`），再在该目录里逐个
`matchPatchName`：命中 → MOD（覆盖内容），没命中 → 新增。
Go 版早期在文件行上直接 `ReplaceNodeContent(rowPath)`，**不看拖进来的文件叫
什么名字** —— 把 `B.jar` 拖到 `A.jar` 那一行，A 的内容被换成 B 的、名字还留着
A，等于静默改错文件。

改成：文件行先 `parentLoc` 退回父目录，再按名字匹配。这样"落到哪一行"只决定
**目标目录**，不决定"改哪一个"。

### 2. "同名"的判定原来是全等

原版 `matchPatchName`：应用节点是 `.jar` 时**前缀匹配**（`appNode.Name` 以
补丁名开头），其余全等。Go 版 `addOrReplaceChild` 写的是 `c.Name == name`，
于是"拖一个短名字的 jar 覆盖长名字的"在原版能命中、在 Go 版会变成新增。
改用现成的 `service.MatchPatchName`（README 匹配那边早就移植过了）。

### 顺带

`addOrReplaceChild` 返回值从 `*State` 换成 `*addOutcome{State, Loc, Replaced}`：
- `Loc` 不能由前端用 `join(dir, 拖入文件名)` 猜 —— 前缀匹配可能命中**不同名**的
  节点（拖 `foo.jar` 命中 `foo-1.2.3.jar`），高亮会跑偏；
- `Replaced` 让提示文案能如实说"已替换"还是"已加入"（原来一律 add）。

### 教训

- **"落到哪"和"改哪个"是两件事**。用落点直接决定改哪个对象，等于把"用户瞄准的
  那一行"当成"用户要改的那一行"，名字不同时就成了静默改错文件。
- 移植时凡是"比较名字"的地方，都要回去翻一眼原版是不是全等 —— 这个项目里
  `.jar` 前缀匹配是个反复出现的特殊规则（README 匹配、拖放匹配都用它）。

## 树里文件排序是乱的（显示顺序 ≠ 存储顺序）

用户："文件现在排序是乱的，能不能按照字母顺序排列"，截图是 `BOOT-INF/lib`
下一堆 jar 完全无序。

**不是 bug，是原版行为**：`SortLinkedList.add` 里那段有序插入被注释掉了，
只剩 `super.add(t)` —— 所以界面显示的就是 zip 条目的**物理顺序**，由打包工具
决定。Go 版 `pack.buildFromZipReader` 末尾也明确写着"不排序"，理由是排序会让
重打包出的条目顺序与原版分叉。

### 改法：只排视图

`gui/app.go` 的 `toView` 是唯一构造 `NodeView` 的地方（`state()` 和
`ExpandNode` 都走它）。在它里面**复制**子级切片再 `sort.SliceStable`，
不碰 `n.Children`：

- 显示：目录在前 + 名字忽略大小写升序（`lessForDisplay`）；
- 存储：仍是 zip 物理顺序 → 重打包、黄金基准都不受影响。

`TestTreeViewChildrenSortedForDisplay` 两头都断言（视图有序 + 内部树仍是
`zeta, alpha, Middle, beta, dir, Aa`），否则"顺手把树也排了"这种改法测不出来。
真实包 228 条 lib 实测从 `accessors-smart` 起严格升序。

### 教训

- **"排序"先问是排显示还是排存储**。这个项目里树的顺序承载了"重打包时的条目
  顺序"，直接排树会把输出包改掉；排视图副本才是零风险的。
- 同一份数据在前后端各有一份表示时，**只改一份**要能说清另一份为什么不用改。

## 补丁树 → 应用树的窗口内拖放（新能力，不是修 bug）

用户："在右侧打开这样文件后，右边的文件不能拖动放在右侧，这是啥原因"。

### 先查是不是回归 —— 不是

前端两棵树**都没有拖放源**：`makeRow` 从不设 `draggable`，只有右侧
「拖入的文件」条那几行能拖（`dropfile-item`）。后端也没有任何"树 → 树"的
映射入口。所以这条能力**压根没移植过**，不是这轮改坏的。

方向问过用户，选了「补丁树 → 应用树」。原版也只允许这一个方向：
`FileTreeCell.onDragOver` 里 `dragInfo.getOriginTree() == getTreeView()`（同树内）
和 `getTreeView() != appTree`（落点不是应用树）都直接 `return`。

### 规则（照 TreeNodeTreeMatchProcessor）

- 落点只决定**目标目录**：目录行是它自己、文件行退回父目录；
- 文件身份仍由 `MatchPatchName` 按名字定：命中 → MOD，没命中 → 造
  MappedNode（文件）/ VirtualNode（目录）按 ADD 绑定；
- 单个**目录**落到**目录行** → 把子项逐个并进去（`matchWithDir`）。

### 两处自己拿主意的地方

1. **已映射的节点允许改指**。原版 `isHasMappedNode()` 为真就拒绝整次拖放，
   而打开补丁包时自动匹配几乎把节点都映射过了 —— 照搬等于这条拖拽平时用不上。
   改成"先 `CleanMappedNode` 解绑旧位置再落到新位置"，统计不会翻倍
   （`TestApplyPatchTwiceDoesNotDoubleCount` / `RemapsFromOldPlace` 钉住）。

2. **包根行必须当容器**。应用包根节点是**文件节点**（对齐 Java 的 FileNode）
   且 `Parent == nil`，早期写法 `tar = tar.Parent` 会把整次拖放**静默丢掉**
   （用户看到"拖了没反应"）。而且新节点的 `Path` 不能拿根节点的**磁盘路径**
   去拼 —— `GetNodePathByParent` 在这里只能返回 `/`，`inheritRawPath` 会拼出
   `D:/x/app.jar/中文.docx` 这种"条目名"写进包里。两处都按
   `appNode.Parent == nil && !appNode.Dir()` 单独处理。

### 通道

走 HTML5，不走 Wails 原生通道：原生那条 `draganddrop.js` 开头判
`types.includes("Files")`，内部拖动没有 `Files`、根本不触发，两边不会打架。
落点判定抽成 `paneSideAt`（`initListDrag` 与 `initTreeDrag` 共用）。

### 定位串

嵌套 jar 里节点 `Path` 是相对那个 jar 的，全树可能重名。前端 `locOf` 按
"父行是不是压缩包"递归拼 `jar!/` 前缀（`parentRowOf` 靠 box 的前一个兄弟找父行
—— 行与它的子级容器是**兄弟**，祖先里没有 `.row`），后端 `resolveIn` 递归解析。

### 教训

- **"拖不动"先分清"没接上"和"接错了"**。这次是能力缺失，不是回归 ——
  先看 `draggable` 有没有被设过，比读一堆拖放逻辑快得多。
- 树的**根节点**是个反复踩的坑：它语义上是"整个包"、结构上是个没有父级的
  文件节点。凡是"退回父目录"的逻辑都要给它留例外。

## 拖入同名文件时先比 md5，相同就不替换

用户："从外面拉入文件到对应位置时，如果存在同名的文件，则迅速做出 md5 比较，
如果 md5 相同的话警示一下。这个你觉得有必要嘛" —— 答"有必要，但别做成弹窗"。

### 为什么值得做（成本几乎为零）

- 拖入文件的 md5：`DropResult.SrcMd5` 本来每次拖放都在算（`fileMd5` 三个调用点）；
- 目标节点的 md5：`toView` 里 `Md5: n.GetMd5OrInit()`，显示在树上的行全都有缓存。
- 增量只是一次字符串比较。

### 为什么做成"跳过"而不是"警示后仍替换"

`ReplaceNodeContent` 无条件 `SetEdited(true)` + 清空 `Md5`。拖一份**字节完全相同**
的文件进来，界面照样打「已修改」星号 —— 用户以为改了，保存出来一个字节都没变。
假改动比"少一个提示"更难受，所以检测到相同就**什么都不做**，回一个 `same` 动作。

### 三处入口

1. `addOrReplaceChild`（直接拖到目录行 / 空白处）→ `sameContent(c, memo.of(src))`；
   一次拖多个时只有**全部**没改才报 same，否则会说"已加入 N 个文件"却啥也没加。
2. `MatchCandidate.Md5` 随候选下发 → `pendingRow` 在用户**点之前**就挂「内容相同」标签。
3. `pendingApply` 点「替换到选中项」时再拦一道（防清单没刷新时误替换）。

任一侧拿不到 md5 就照常替换 —— 宁可多换一次，也不能因为"算不出来"丢用户文件。

### 顺带

`md5Memo` 让一次拖放里同一个文件只读一遍（143 MB 的胖包全量 md5 约 220ms，
算两遍就是两倍 IO）。只在同名命中那一刻才调用，新增路径零额外 IO。

### 教训

- 用户提"加个提示"时，先问**这个提示要挡掉什么后果**。这里真正的后果不是
  "不知道内容一样"，而是"被打了假改动标记"，所以解法是跳过而不是弹窗。
- 新加一档状态时，**颜色语义要跟着走**：same 用中性灰，不能用绿色
  —— 绿色是"改成了"，这里恰恰是"不用改"。

## 补丁包根行也要能拖（"右侧的 jar 包拖不到左侧"）

用户截图：右侧「补丁包」面板里只有**一行** —— `xxl-job-core-3.6.0-SNAPSHOT.jar`，
就是这个包本身。上一轮我把 `depth > 0` 写进了可拖条件，于是根行拖不动。

### 根行该做什么

补丁包本身是个 `.jar` 时，树上唯一那一行就是根行。它的语义只能是
**"把整包套到应用树上"**（顶层条目逐个按名字匹配进落点目录），不可能理解为
"在应用树里找一项叫 `xxl-job-core-3.6.0-SNAPSHOT.jar` 的东西"。

- `isTreeRoot(n)` 按 `Parent == nil` 判（不要用 Path：根节点的 Path 是磁盘路径）；
- `ApplyPatchNodesToApp` 里 `(el.Dir() && appNode.Dir()) || isTreeRoot(el)` 都走
  `matchPatchChildrenInto`；
- `DropPatchNode` 用 `isRootRow(treeSidePatch, p)` 认根行，直接取 `RootNode()`；
- 前端去掉 `depth > 0`，另加 `cursor: grab` 让"能拖"看得出来。

### 顺带挖出两个 bug

1. **README 会被并进应用树**。整包拖过来会扫到补丁根下的 README，不跳的话
   应用树里凭空多一个 `README.txt` 的 ADD 节点。`matchPatchChildrenInto` 里
   按 `TreeNodeTypeReadme` 跳过。
2. **`CreatePatchDiffInfo` 拿两个空 md5 判"内容相同"**。目录的 `GetMd5OrInit`
   恒为空（`ConsumeBytes` 对目录直接返回），于是每走进一个目录就往
   `PatchDiffInfo` 里塞一条"是同一个文件"的假提示。整包套用会把每个目录都走
   一遍，提示里就全是目录名。改成任一侧为空直接不比。

### 教训

- **"拖不动"要看是不是唯一的入口**。排除根行的理由（"误触代价太大"）在
  "补丁包就是个 jar" 这个真实用法下完全不成立 —— 因为那是**唯一**能拖的东西。
- 新开一条批量路径（整包套用）时，要把沿途"只在单点场景下才安全"的假设
  重新过一遍（README、空 md5 这两条都是这么暴露的）。

## 更正：拖根行 = "把这个 jar 放进那个目录"，不是"整包套用"

用户："我把右侧的 jar 包拖动拉到 lib 文件夹下面时，他把 jar 包分解放里面了，
是不是有问题。"

是我上一轮判断错了。我把"补丁包根行"理解成"整包套用"（并子项），于是拖到
`BOOT-INF/lib` 上会冒出 `com/`、`META-INF/`。根行代表的是**那个 .jar 文件本身**，
拖过去就是"把这个 jar 放进 lib"——和从资源管理器拖一个 jar 进去同一条规则。

### 改法

- `ApplyPatchNodesToApp`：只有 `el.Dir() && appNode.Dir()` 才并子项，根行走按名匹配；
- `matchOnePatchNode`：`recurse := el.Parent != nil` —— 拖整包匹配上之后**不再合并
  子项**（包里的东西已经整份在新 jar 里，再逐条 ADD 只会把统计算多、看着更像"被拆开"）。

### 顺带修了上游的一个真 bug

`writeTreeNode2PackWithJar` 只看 `children`、**完全不看 `MappedNode`**：children 为空
写自己的字节、有就重打包旧子级。于是"把 jar 整个换进 lib"保存出来**还是旧 jar**，
README 里对 jar 写 `!路径` 也一样静默无效。判据改成"节点自己有没有绑定"——不能靠
children，因为树上的 jar 只要展开过就有 children（那是显示用的）。

`TestSaveAppPackWritesReplacedWholeJar` 钉住：保存后读回该条目必须是补丁 jar 的字节、
且是能解析的 zip。

## 拖拽改成长按起拖（300ms）

用户："太容易误触，改成长按才拖。"

**不能**靠"长按到了再把 draggable 设成 true"：Chrome 只在 mousedown 那一刻判定元素
可拖（Blink 的 `mouse_down_may_start_drag_`），中途改对本次手势无效。
正确做法：始终可拖，在 `dragstart` 里检查 `armed`，没按够就 `preventDefault`。
`dragstart` 只在真移动时派发，所以"按住不动 → 够时长 → 再移动"就是长按起拖，
"一按就甩"被挡掉。

配套：`DRAG_ARM_MS = 300`；`armed` 后加 `.drag-ready` 把光标从 grab 变 grabbing；
CSS 里**不要**用 `:active` 变 grabbing（一按下就变，会和门槛打架）；行 title 里
补一句"按住约 0.3 秒后拖动"。

### 教训

- **同一个手势在两种语义下都"讲得通"时，要按用户的实际操作序列选**。
  "根行 = 整包"在抽象上成立，但用户手上有的是"一个改过的依赖 jar，要塞进 lib"。
- 改语义之后要顺着走完**写出**那一端：映射建对了、界面标了 MOD，写出还拿旧字节，
  这种"假绿"最难发现。

## 拖拽光标：平时箭头，长按够时长才变小手

用户："能不能正常情况下鼠标样式还是正常的，长按之后变成小手"。

之前 `.row[draggable="true"] { cursor: grab; }` 是常驻抓手 —— 为了让"能拖"看得出来，
但代价是整片补丁树一直顶着抓手光标，和普通行的点击手感不一致，也变成视觉噪音。

改法只有一条 CSS：删掉 `[draggable]` 那条，`.row.drag-ready { cursor: grab; }`
（原来是 grabbing）。JS 那边一个字没动 —— `armed` 后加 `.drag-ready`、
`mouseup` / `mouseleave` / `dragend` 移除，本来就是这个节奏。

细节：
- 用 `grab`（张开的手）而不是 `grabbing`（握拳）—— 门槛是"可以抓了"，还没抓住；
  而且真正拖起来之后 cursor 由浏览器接管，`grabbing` 根本显示不出来。
- **不能**用 `:active`：一按下就变，会和"按够 0.3 秒才允许起拖"的门槛打架，
  用户会以为已经能拖、一甩却被取消。
- 按住不动 → 够时长变小手 → 松手不变（`mouseup` 立刻回箭头），所以它只表示
  "这一刻能拖"，不会赖在界面上。

### 教训

"可拖"的可发现性不该靠**常驻**样式解决。常驻提示是噪音，随状态出现的提示
才是信号 —— 悬停提示里那句"按住约 0.3 秒后拖动" + 按够时长变小手，
两者合起来比一个永远的抓手更清楚。
