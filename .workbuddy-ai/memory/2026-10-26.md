## 「差异块逐行描框」改成块级竖线标记

用户 2026-10-23 发了张 20 行差异块的截图："为啥每一行要这么框出来，太影响美观了"。

### 改法

旧：`.nav-current { outline: 2px solid var(--accent); outline-offset: -2px }`
—— 块里多少行就叠多少个框，像梯子，还把正文逐行横切。

新：**IDEA 式块级标记**，两条通道分工
- 行号列**最左** 4px 色条 = `mark-*` 语义色（增绿 / 删灰 / 改浅蓝）
- 行号列**最右** 3px 竖线 = `--accent` 位置色（当前跳到哪）
- 再叠一层极淡 `--nav-wash` 洗色

关键约束：底色只能用 `background-image` 叠层，**不能写 `background-color`**
—— 差异行本来就有 `mark-*` 底色，写 color 会整条替换掉，语义色就没了。
有 mark 的行把它的 4px 色条带到第三层（特异性 4 类 > 3 类，不用 !important）。

### 顺带挖出的两个隐性 bug（比原报障更严重）

`.ln` 拆列后成了 inline 盒：
1. **只有文字那么高** → 竖线渲染成 20 段虚线
2. **丢了 line-height 继承** → 一路拿到 body 的 1.5 = **21px**，正文 `.cline`
   是 17px，**每行错 4px**；40 行时行号列 scrollHeight 1260 / 正文 1020，
   **行号会指向错误的代码行**

修法：`.code-gutter .ln` 写死 `display: block` + `line-height: 17px`。
（`font-family: var(--mono)` 是同一个继承链断裂的坑，前一天已修。）

### 为什么以前没发现

mock 差异块**最大只有 2 行**，2 行错 4px 肉眼看不出来。
新增 `shot_nav_block.py`：把 `OpenContent` 包一层，返回"40 行文件、第 10~29
行全 mod"的载荷，走真实双击 + 点「下一个差异」，20 行块才把问题顶出来。

### 验证方式换了：不靠肉眼，量几何

本会话模型**看不了 PNG**，所以写了 `_measure_gutter.py`：`--dump-dom` 取回
页面内量好的 JSON（base64 塞进 `<pre id="__M">` 避免转义），三套主题断言：
- `heights=[17]` 全部等高
- 相邻行 **maxGap = 0** → 竖线连续，不是虚线
- `gutterScrollH == codeScrollH == 680` → 不漂移
- 两栏各**正好 20 行** `nav-current` → 整块标记，不是一行
- `.ln` 的 background-image 里确有 accent 的 `3px` 渐变

结果 **ALL PASS**（light / graphite / oled）。

⚠️ 写断言时踩了自己的坑：split 视图**左右各有一份** gutter / code，
在 `body` 上数 `.gline.nav-current` 会把两栏加起来（20+20=40），
误判成"整篇都被标记"。必须**按单栏**数（`g.querySelectorAll`）。

### 产出

- `_measure_gutter.py`（新）：三主题几何断言，全绿
- `shot_nav_block.py` / `shot_diff_idea.py`：`_extract` 脚手架已不在工作区，
  `refresh()` 加了"源不存在就跳过"，否则截图直接 FileNotFoundError
- 重出截图：`nav-block-*` / `nav-block-zoom-*` / `diff-idea-*` / `diff-idea-zoom-*`
- `wails build -tags webview2` 重跑，`gui.exe` 已更新（**42126848** 字节），
  确认新 CSS 嵌进去了（`1f6fb2` / `999px`×12 / `nav-wash`×8）
- `go vet` 干净，`go test ./...` 全绿
- `MIGRATION.md` 新增一行偏差登记（逐行框 → 块级竖线 + 4px 漂移）

### 教训

- **`display: block` 不只是"让背景铺满"**：它同时决定相邻行的盒是否首尾
  相接。inline 盒配渐变背景 = 逐行虚线。
- **拆 DOM 结构时，所有靠继承拿到的属性都要重新点名**。`.ln` 从 `.code`
  的子节点变兄弟后，`font-family` 和 `line-height` 先后各炸一次，症状一个
  是列宽不齐、一个是行号错行 —— 同一类错误，两个不同的脸。
- **mock 数据的形状要覆盖真实数据的极端**。2 行的假差异块让"逐行框"
  和"4px 漂移"两个问题都藏了好几天。

## 双栏对比「代码没有高亮」（>64KB 整篇放弃）

用户："两个对比的，代码没有高亮"（截图 `AccountSpecialService.class`，
两栏一片黑字）。

### 根因

不是配色、不是 lang、不是 CSS。是原版 `computeHighlighting` 里那句
`if (text.getBytes().length > 64 * 1024) return null;` —— **超 64KB 整篇
不高亮**。`.class` 反编译的 Spring service 上千行，实测 **1200 行 = 76,890
字节**，正好越线。

### 排查路径（三步排除法，值得复用）

1. `go run` 打印 `RenderMarked` 的片段 → 后端确实吐 `class:"keyword"`，
   `LangForExt("class") == "java"`。**后端没问题**。
2. 真 Chrome 渲染带 token 类的双栏载荷 → `.keyword` computed color =
   `rgb(128,0,128)`。**CSS/DOM 没问题**。
3. 1000/1200/1500 行梯度跑 `Tokenize` → 1000 行（63,890 字节）11001 个区间，
   1200 行**直接 0 个**。**锁定 64KB 闸门**。

### 改法

64KB 从"整段上限"降级成"**切块大小**"：超过就按**行边界**切块、逐块分词、
偏移加块起点再拼。单次正则规模仍钉在 64KB 内。
切点退到最后一个换行**之后**，不劈开一行；单行超 64KB（压缩 js/css）才硬切。
代价：`/* */` 恰好跨块边界时认不出（罕见）。

性能（一次性、后端算）：1200 行 13ms / 5000 行 62ms / 10000 行 135ms /
20000 行 246ms，线性；关键字计数与切块前**逐行一致**。

### 黄金基准的偏差处理

`hl_ref.tsv` 是 Java 原版真实输出，有一条 >64KB 用例期望 `NULL`，现在变 `OK`。
这不是移植错误 → 在 `highlight_golden_test.go` 里单列 `deviate` 分支
（限定 `want==NULL && len>64KB && got==OK`），不计入通过率。
结果 **202/202 + 2 条刻意偏差**。

新增 `TestHighlightLargeFileKeepsKeywords`：不只断言非 nil，还要求
keyword/string/comment 各 1200 行全认出来（3600/1200/1200），且区间
**连续覆盖全文、无空洞**。

### 端到端验证

`_measure_highlight_big.py`：`genview/` 里用真实 `RenderMarked` 生成
79,394 字节双栏载荷 → 喂给前端 → 量到 3604 个 keyword 全 `rgb(128,0,128)`、
1200 个 string `rgb(0,0,255)`、2400 个 comment `rgb(95,158,160)`。
截图 `hl-big-light.png`。

### 产出

- `gui.exe` 重建 **42128384** 字节（08:58）
- `go vet` / `go build ./...` / `go test ./...` 全绿
- `MIGRATION.md` 新增一行偏差登记
- `gofmt -l` 只报了 `internal/manualdel/manualdel.go` / `gui/search.go` /
  `gui/search_test.go` 三个**本次没动过**的文件（历史遗留），未碰

### 教训

- **"某个文件没有高亮"不等于"高亮坏了"**。先找**触发条件**（这里是文件
  大小），别一上来怀疑样式。
- 三步排除法（后端数据 → CSS 计算值 → 边界梯度）比反复看截图快得多，
  尤其在我看不了图的时候。
- 跨语言黄金基准遇到"刻意增强"时，**别改参考数据**，在测试里单列偏差分支，
  把"为什么不一样"写进注释。

## 快速滚动时行号列与正文列脱节

用户："按住上下快速滑动时，会短暂出现这个情况"（截图右栏只剩一串行号、
正文空白，行号与代码对不上）。

### 根因（量出来的，不是猜的）

行号列与正文列是两个独立滚动容器，纵向靠 `scroll` 事件同步；而**两栏之间**
的同步是"设对方的 scrollTop"，这会触发对方**下一帧**才派发的 `scroll` 事件
→ 被镜像那一栏的行号列要等两跳。

`probe_sync_desync.js`（CDP 真实时间，每帧 60px，180 帧）：
- `max-pane-diff = 0` —— 两栏正文始终同步（之前担心的没问题）
- `max-gutter-lag = 120px` —— 被镜像那栏的**行号列每帧落后 7 行**
- 样本 `f1: code1=60 gut1=0`

### 改法

`syncScroll` 里设完 `dst.scrollTop` 之后**当场**把它的行号列也推过去，
不等它自己的事件。不回环：对方事件下一帧到达时两值已相等，直接跳过。

四档步长（60/200/400/800）× 左右两栏分别驱动 → 全部 **0px**。

### 顺带修的末尾错位

`.code` 有 15px 横向滚动条、`.code-gutter` 没有（overflow:hidden），
所以正文能多滚 15px → 滚到底时行号比代码低一行。
新增 `fitGutterTail`：把 `offsetHeight - clientHeight` 补成行号列的
`padding-bottom`（加在内容之后，不挪动任何一行），渲染后推一帧量一次；
窗口缩放由已有 `ResizeObserver` 调 `refitGutters` 重量。

### 性能

`probe_scroll_frames.js 3000`：avg 16.7ms / p95 16.8ms / 掉帧 0%，
每帧 JS 0.063ms —— **未回退**。

### 产出

- `gui.exe` 重建 **42131456** 字节（09:09），已确认 `pullGutter` /
  `fitGutterTail` 嵌进去了
- `MIGRATION.md` 新增一行偏差登记
- 新增探针 `probe_sync_desync.js`（支持步长 + 驱动哪一栏两个参数）

### 教训

- **"两个滚动容器靠 JS 同步"必然慢一帧**，而且会**链式叠加**：
  A→B 一帧、B 的 gutter 再一帧。同步时必须**当场**把所有下游一起推完。
- 采样时机决定结论：先设 scrollTop 再读，量到的是"事件还没派发"的中间态
  （120px 里有一截根本看不见）；**在 rAF 开头先采样**才是"上一帧真正画出去
  的样子"。这次两种顺序都跑了，才分清 `max-pane-diff` 是 0 还是 120。
- 滚动条厚度会改变 `scrollHeight - clientHeight`：一个 `overflow:auto`、
  一个 `overflow:hidden`，可滚范围天然差一条滚动条。

## 打开包 400MB 内存 + 对比窗口卡顿

用户三连报障："打开包之后占用 400 多内存"、"对比窗口一出来有点卡顿"、
"左侧 jar 不支持其他 jar 直接拖入"。

### 内存：`io.ReadAll` 把整个 jar 钉在堆上

`GetAppTreeInfo` 走的是 `pack.BuildZipTreeFromReader` → `io.ReadAll`，
143 MB 的 `1.jar` 整个读进内存，而且**树活着期间一直挂着**（zip 的
`ReaderAt` 要它）。改成新增的 `pack.BuildZipTreeFromPath`
（内部是 `reopenReaderAt`：每次 `ReadAt` 现开现关），只读中央目录。
实测 **打开 309ms、堆增量 0 MB**（原来约 143 MB），691 节点。
补丁侧 `doGetTreeNodeWithCompress` 同样改掉。

中途踩过两个坑：先试过让 `tree.Info` 持有 `*os.File` 并 `Close()`，
结果 Windows 上 `TempDir RemoveAll` 报 `being used by another process`，
~20 个测试连环失败 —— 句柄所有权这条路是错的，**改成路径式按需开**才对。

### 对比卡顿：md5 算了一堆没人看的东西

`ComparePacks` 对**两个包的每个条目**都解压算 md5。143 MB 包实测
中央目录 **1ms** / 全量 MD5 **222ms**，两个包 444ms，端到端 498ms。
而那 651 个条目两侧完全一致，md5 一个都不会被展示。

改成两段式（`packSource`）：`scanZipMeta` 只扫中央目录拿
`size + CRC32` 判同异（zip 规范保证这两项都在中央目录里，不用解压）；
`digestZipEntries` **只对要展示的条目**（不同 / 仅 A 有 / 仅 B 有）算 md5。
**498ms → 3ms**；最坏情形（全"仅 A 有"）470ms → 249ms，因为只读需要展示的那一侧。

口径变化：判"相同"从 md5 降到 size+CRC32（1/2^32 碰撞）。只影响对比
对话框展示、不参与补丁匹配，已登记 MIGRATION.md。

`TestComparePacks_SameEntriesAreNotRead` 用"数据改过、中央目录 CRC 还是
原内容"的 STORED 条目钉住"相同条目不读"——真读了会撞 `ErrChecksum`；
另加对照组（落进"仅 A 有"就必须读、必须报错）证明断言不是空过。

### 教训

- **`io.ReadAll` 一个包 = 把包钉在堆上**。要拿 zip 目录用
  `zip.NewReader(ReaderAt, size)`，别再往下 `ReadAll`。
- **先量再改**：`_cmpctrl` 把"中央目录 / 全量 MD5"分开计时，一眼就看出
  444ms 全是白干的；不拆开就只能瞎猜。
- 判"两个文件是否相同"的最便宜答案通常**已经在元信息里**（size+CRC），
  哈希只在要**展示**的时候才需要。

### 拖 jar 到左树：分流顺序搞反了

用户："左侧 jar 包不支持其他 jar 包直接拖入，应该和文件一样"。

先排除了"没接线"：Wails 的 `OnFileDrop(cb, true)` 靠 `elementFromPoint` +
`--wails-drop-target`（`.pane` 声明、子元素继承）判落点，探针在四个落点
（正中/第一行/左下空白/标题栏）都拿到了 `HandleDrop:app:…`；后端
`isPackExt → HandleFileDrop → OpenAppPack` 也通。

**真因是分流顺序，对照原版源码才看出来**。原版是两层处理器：
- 落在**单元格**上 → `FileTreeCell.onDragDropped` → `TreeNodeFileMatchProcessor`，
  `source == null`（从系统拖进来的）时**任何**文件都收，**jar 和 .class 一视同仁**，
  按 `matchPatchName` 在目标节点/父目录里找同名项：命中 → `mappedNode(MOD)`，
  没命中 → `createAndGetAppNode(ADD)`；
- 落在**空白处**才冒泡到 `HomeLeftTreeView.onDragDropped` → `refreshAppTree`，打开整包。

Go 版把 `isPackExt` 放在最前面 → 拖 jar 到 `BOOT-INF/lib` 上会**换掉整个应用包**，
用户的感受就是"不支持把 jar 拖进来"。

**改法**：行优先分支提到整包判断之前，且**只对 `treeSideApp` 生效** ——
原版补丁树单元格压根不接拖放（`getTreeView() != appTree` 就 return），
一刀切会让补丁树开始接包内文件。目录也不走这条（原版是 `matchWithDir`，
Go 版没实现）。顺带修掉：文件行上拖多个时目标退回**父目录**
（原版 `appNode.isDir() ? appNode : appNode.getParent()`），新增 `parentLoc`
要认 `jar!/` 前缀。

界面上两个 `.pane-head` 加了 `title` 说明分工；`trackDropRow` 的注释原来写的
"文件行亮 = 会替换这个文件"对整包是**错的**（行亮但松手是换整包），现在才对。

### 教训

- **"拖进来没反应/反应不对"要先分清是接线问题还是语义问题**。探针证明接线
  没问题之后，就该去读原版源码比行为，而不是继续在 Go 侧猜。
- **事件处理器是分层的**（单元格 vs 容器），JavaFX 里靠 `consume()` 决定谁赢；
  移植到"一个后端方法 + 前端传落点"的模型时，**这个优先级必须显式写出来**，
  否则默认顺序会悄悄改掉语义。
- 改分流顺序一定要问一句"另一侧会不会被牵连"—— 补丁树的单元格根本不接拖放，
  这条约束只在原版源码里，Go 侧看不出来。

### 根行是个坑

前端 `renderTree` 渲染的就是 `state.appTree` 这个**根节点**，所以"根行"也会
被当成普通行传 `rowPath` —— 而根节点的 `Path` 是**磁盘路径**
（`D:/.../app.jar`），不是包内路径。照普通行走会 `resolveNode` 失败、
报"树里找不到节点"。

新增 `App.isRootRow`（`rowPath == ""` 或等于 `treeRoot(side).Path`）把它归到
"空白处"：拖整包到根行 = 换这个包，拖普通文件 = 加到根目录
（后者顺手修掉一个既有的报错）。`TestHandleDropOnRootRow` 钉住。
