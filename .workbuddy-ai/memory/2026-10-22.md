## 全局暗黑主题：从两档扩到三档（明亮 / 石墨 / 纯黑）

**背景**：2026-10-21 已按用户选定的"方案 C 纯黑 OLED"落地了 `data-theme="dark"`
一套暗色；本次用户要求"把石墨也增加上，选择多"，最终三档。

**用户偏好**：主题选择权交给用户，不替她定。她看过三套预览（A 石墨 / B 深空蓝 /
C 纯黑 OLED）后先选 C，次日主动要求补上 A。

### 改动

- `app.css`：`dark` 正名为 `oled`；新增 `:root[data-theme="graphite"]` 变量块
  + 同名 `.lang-*` 语法覆写（One-Dark 经典配色 `#c678dd/#e06c75/#56b6c2/#98c379/
  #7f8794/#d19a66`，比纯黑那套柔一档）。两套暗色共用全部规则，只差变量值。
  - 石墨的 `--code-ln-edge` 取 `#2f343c` 而非 OLED 的 `#262a31` —— 石墨的
    `--surface-2` 正好就是 `#262a31`，行号栏分隔线用那个值会和两侧糊在一起。
- `app.js`：`THEMES = ['light','graphite','oled']`；`currentTheme()` 只认这三个值，
  别的（含旧的 `'dark'`）回落亮色。`applyTheme()` 同步窗口底色。
- `index.html`：`<head>` 引导脚本认 `graphite`/`oled` 两个值；「设置 → 常规配置 →
  主题」下拉三选项（明亮/石墨/纯黑）。
- Go 侧沿用上一轮的 `SetWindowBackground` + `main.go` 的 `BackgroundColour`。

### 两个值得记住的坑

1. **headless 的 `--virtual-time-budget` 不推进 CSS 过渡时钟**。验证脚本把
   localStorage 的 seed 放在 body 里（app.js 之前），启动时先按亮色画一帧再被
   `initTheme()` 翻暗，触发 `.btn` 的 120ms 过渡，而虚拟时间把过渡冻在起点 ——
   `getComputedStyle` 量出来的 `background-color` 一直是亮色的，一度误判成
   "令牌没生效"。加 `* { transition: none !important }` 后立刻正确。
   **真实应用没这问题**：`<head>` 引导脚本首屏就设好 `data-theme`，不会亮一下。
2. **从 Python 源码里按原文切多行字符串会把转义搬错**。抽 `AUTO` 脚本时用
   `src[i:j]` 切片，`'\\u25B8'` 没被 Python 解释成 `'\u25B8'`，JS 里成了字面量，
   导致 twisty 判断永不相等、树一个都不展开。要么 `exec` 取变量，要么别抽。

## 「拖入的文件」条目补 MD5（当天下午，用户报障）

用户截图报："拖动了单个文件之后，右侧没有显示文件的md5值"。

### 根因与分工

- 包内节点的 md5 走 `GetMd5OrInit()` 缓存，缓存的是**包内**那份字节；
  拖进来的文件此刻只是磁盘上一个路径，两边不是同一份内容，**不能复用**。
- 原版 `FileTreeCell` 给树上每个文件行都渲染 `日期 + 大小 + md5`，
  `FileDirectNode` 注释即"文件节点，直接由系统拖入"—— 拖入文件同样算 md5，
  所以这是 Go 版漏了一项，不是新增能力。

### 改动

- `internal/util/hash.go` 新增 `Md5Stream(io.Reader)`：流式算，不 `ReadAll`
  （拖几百 MB 的包进来不能先整份读进内存）。
- `gui/app.go` 新增 `fileMd5(path)`：读不到就空串（混进读不了的文件不能让
  整条链路报错）。`DropMatch` 与 `DropResult` 各加 `SrcMd5`，在 `HandleDrop`
  的替换 / 反查 / 新增三条返回路径和 `matchLooseFilesIntoApp` 的逐文件
  `Items` 里都填上。
- `app.js`：`showDropFile` 的记录从 `{path,size}` 扩成 `{path,size,md5,...}`；
  `setDropFileSizes` 改名 `setDropFileMeta`，**按 `srcPath` 对齐而不是按顺序**
  （后端 Items 顺序虽与拖入顺序一致，按路径匹配将来乱序也不会错位）。
  两个值都是"拿不到就留空"，绝不拿 0 或假值糊上去。
- `app.css` 新增 `.dropfile-md5`（等宽字体、`user-select: text` 方便复制）。

### 顺手修的泄漏

`.statusbar` 的 `box-shadow: 0 -1px 2px rgba(16,24,40,.04)` 是写死的亮色值，
两套暗色主题都没翻。收成 `--bar-shadow` 令牌（不复用 `--shadow-sm`：那个是
"控件四周一圈"，这里只往上一面且强度弱得多）。

### 验证

- 三条 Go 单测：`TestFileMd5`（含 1 MB 流式、不存在路径、目录三个分支）、
  `TestDropLooseFilesReportSrcMd5`（matchMany/零命中/逐文件 Items）、
  `TestDropRowAndDirReportSrcMd5`（replace / add 两条路）。
- `go vet` 干净；`go test ./...` 全绿；`wails build` 成功，`gui.exe` 已更新。
- 走查 313/317，仍是基线那 4 条既有失败；新增 3 条 MD5 断言全 PASS。
- `.workbuddy-ai/mockups/verify_statusbar_shadow.py`（新）：三套主题下量
  `.statusbar` 计算样式，`rgba(16,24,40,.04)` / `rgba(0,0,0,.45)` /
  `rgba(0,0,0,.5)` 三档全对。
- `.workbuddy-ai/mockups/shot_dropfile_md5.py`（新）：三套主题 + 一张"改动前"
  对照的截图（对照页用 `.dropfile-md5 { display:none }` 藏掉，而不是猴 Patch
  `createElement` —— 藏掉它视觉上就等于"这一行从来没有 MD5"，且不碰渲染逻辑）。

### 踩的坑（重要）

**mockups/ 下那份 `mock-backend.js` 是"不存在才拷"的派生副本，早就过期了。**
probe_frontend 里给它加了 `HandleDrop`（带 `srcMd5`）之后，mockups/ 这边始终
没跟上，于是拿它连截四张图，条里都只有名字没有体积和 MD5，白折腾半天。
三个脚本（`verify_themes.py` / `verify_statusbar_shadow.py` /
`shot_dropfile_md5.py`）已统一改成**每次强制同步**，并各自留了注释说明为什么。
**派生资源没有"只拷一次"的道理。**

## 「单包视图」按钮文案不跟着状态走（当天傍晚，用户报障）

用户截图报："在双栏下，点击单包视图，会只显示 jar 页，但是上面还是单包视图，
我希望切换双栏时这个按钮名称是变动的"。

### 根因是两处，不是一处

1. **文案写死**。`index.html` 里 `<button id="btn-single-view">单包视图</button>`
   是静态文本，点了只切 `body.single-app`，从不改自己的字。
2. **选中态压根没样式**（这条更要命）。`app.js` 里一直在
   `this.classList.toggle('active', on)`，但 `app.css` 里**从来没有 `.btn.active`
   规则** —— 加了 class 没有任何视觉效果，按钮在单包视图下和静止态一模一样。
   等于唯一的状态提示是假的：布局确实变了，但按钮本身毫无反应。

### 改动

- 文案写的是**"点一下会切到哪个视图"**（不是"现在在哪个视图"）：
  双栏 → 「单包视图」，单包 → 「双栏视图」。`title` 也跟着翻。
- 新增 `.btn.active:not(:disabled)`：底色 `--row-sel`、文字与描边 `--accent-press`，
  投影换成内凹（和 `:active` 同一套）。**保留渐变高光** —— 不像 `:disabled`
  那样整个去掉，否则会从"陷进去"变成"贴平"。
- 抽出 `syncSingleViewBtn()`，点击后调一次 + 初始化时调一次（原来靠 `this`
  在监听器里改自己，抽出来后更稳，也顺便让初始态有保证）。

### 验证

- 走查新增 4 条：`singleview-click-flips-label` / `singleview-active-has-style` /
  `singleview-title-follows` / `singleview-click-back-restores`（最后一条防
  "只翻过去翻不回来"）。总数 317 → 321，`probe-count` 同步改。
- `.workbuddy-ai/mockups/verify_single_view_btn.py`（新）：5 条断言，
  含".active 必须真的改计算样式"这一条。
- `.workbuddy-ai/mockups/shot_single_view_btn.py`（新）：三套主题 × 双栏/单包
  两种态共 6 张截图。
- `wails build` 已重跑，`gui.exe` 已更新。

### 踩的坑

1. **又是虚拟时间不推进动画时钟**。`.btn` 上有 120ms 过渡，
   `--virtual-time-budget` 只推进定时器，过渡整个冻在起点，
   `getComputedStyle` 量出来一直是切换前的颜色，一度以为 `.btn.active` 没生效。
   走查里在按钮自己身上 `style.transition='none'`（不动全局），量完再还原。
2. **新增断言后走查出现了一条"新"失败 `compare-open-menu-diffmode-routes`**。
   做了对照实验：把新断言整段剥掉跑 5 次全过，加回去跑 2 次里挂了 1 次，
   之后又连续 22 次全过。诊断过：`#content-win` 是顶层元素、不在 `.info-pane`
   里，切换 `single-app` 藏不掉它；虚拟时间也只用了 13.8s / 预算 20s。
   结论是那两次挂在**断言代码还是半成品的时候**（当时 `base()` 把 `.active`
   删了没加回去、且没关过渡），不是产品回归。顺手把那条断言的失败详情补全了
   （报出"有没有找到那一栏 / 菜单里有什么 / content-win 隐不隐藏"），
   以后一红就能自己说清卡在哪一步。
